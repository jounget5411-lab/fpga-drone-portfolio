# 문제를 관찰하고 원인을 좁힌 과정

[프로젝트 소개로 돌아가기](../README.md) · [결과와 측정 조건](results.md)

카메라 입력부터 모델 평가, RTL 수치 표현과 FPGA 메모리 배치까지, 통합 과정에서 발생한 문제를 계층별로 나누어 해결했습니다.

## 1. 검은 화면을 세 계층으로 분리

**문제.** 영상 처리 경로를 추가한 뒤 HDMI가 검게 나오거나 프레임버퍼가 0으로 남았습니다. 카메라부터 다시 고치기에는 원인 후보가 너무 많았습니다.

**관찰.** UART가 어느 초기화 단계에서 멈추는지, 블록 설계의 모듈이 실제 합성 소스에 포함되는지, 첫 픽셀의 `tuser`와 행 끝의 `tlast`가 `valid/ready`에 맞게 진행하는지를 따로 확인했습니다.

**원인과 대응.** 같은 화면 증상에 세 문제가 겹쳐 있었습니다.

| 계층 | 확인한 문제 | 대응과 재확인 |
|---|---|---|
| 소프트웨어 | VDMA 장치 ID와 생성된 플랫폼 정보가 맞지 않아 설정 조회 실패 | 베이스 주소 접근으로 설정 경로를 분리하고 UART 초기화 완료를 확인 |
| Vivado 프로젝트 | 다운샘플러가 도면에는 있지만 합성 소스에서 누락 | RTL과 output product를 다시 등록·생성하고 실제 포함 여부 확인 |
| 영상 프로토콜 | 첫 픽셀의 프레임 시작 신호가 1클럭 어긋남 | 데이터와 SOF/EOL의 파이프라인을 맞추고 프레임 저장·영상 덤프 재확인 |

이후에는 **분기만 추가 → 스트림과 프레임 경계 확인 → 해상도 변경** 순서로 한 변수를 바꾸며 검증했습니다. 320 × 180을 160 × 90으로 줄일 때도 출력 크기뿐 아니라 VDMA stride, 픽셀 폭, 샘플 선택과 backpressure를 함께 점검했습니다.

## 2. 높은 정확도보다 데이터 분할을 먼저 점검

**문제.** SNN 학습에서 매우 높은 수치가 나왔지만 독립된 실제 영상에서는 드론을 놓쳤습니다.

**원인.** 20프레임 윈도우를 한 프레임씩 이동해 만든 샘플은 이웃끼리 19프레임을 공유합니다. 이 샘플을 무작위로 나누면 같은 영상의 거의 같은 장면이 학습과 평가에 동시에 들어갑니다. 카메라 흔들림이나 물체의 상하 위치에 의존하는 현상도 관찰했습니다.

**대응.** 동영상 파일 단위로 학습·평가를 나누고 독립 영상으로 평가했습니다. 사람과 드론이 붙어 있는 장면, 낮게 나는 드론, 배경·위치가 다른 장면을 점검하고 데이터를 보강했습니다. 샘플 수뿐 아니라 영상 간 독립성과 실패 장면을 기준으로 평가 체계를 개선했습니다.

## 3. 정지 입력의 Fly 오판을 비트폭까지 추적

**문제.** 움직임이 없는 입력에서도 출력 뉴런이 발화하거나, 두 스파이크 수가 0:0인데 Fly로 표시되었습니다.

**원인 분리.** 카메라를 분리하고 RTL에 all-zero 입력을 직접 넣어 같은 현상을 재현했습니다. 영상 노이즈에 앞서 신경망 내부의 수치 표현과 비교 조건을 살펴볼 수 있었습니다.

**대응.** 임계값 171·146이 signed 8비트의 양수 범위를 넘어 음수로 해석되는 것을 확인했습니다. 임계값 폭을 16비트로 넓히고, 두 임계값의 GPIO 전달 형식과 동률 판정을 명시했습니다. RTL 단독 입력, 실제 카메라 정지, 손 움직임을 순서대로 넣어 결과를 비교했습니다.

값의 범위, 부호, 전달 비트 배치는 모델과 하드웨어 사이의 인터페이스 사양으로 관리했습니다. 모델 값이 맞더라도 전달 형식이 다르면 결과가 달라질 수 있기 때문입니다.

## 4. CNN 자원 초과에서 메모리 배치를 확인

**문제.** CNN 통합 중 115,200 × 8비트 activation 메모리가 LUTRAM으로 합성되면서 자원 요구량이 급증하고 배치에 실패했습니다.

**분석.** 모델 규모를 바로 줄이기보다 최신 자원 보고서와 계층별 메모리 배치를 확인했습니다. 디버그 레지스터 추가분과 대용량 메모리의 배치 비용을 나누고, 오래된 합성 결과를 보고 있지 않은지도 확인했습니다.

**대응.** 대규모 초기화 루프를 정리하고 메모리의 합성 형태를 수정해 BRAM 추론과 배치를 정상화했습니다. 모델 연산량과 메모리 배치 비용을 따로 분석하면서, 같은 알고리즘도 RTL 표현에 따라 자원 사용량이 크게 달라진다는 점을 반영했습니다.

## 5. RAW 출력부터 보드 통합 경로를 추적

CNN의 testbench에는 출력이 있어도 실제 보드에서 RAW가 0이거나 포화값으로 나오는 경우가 있었습니다. 입력 프레임, 가중치 로드, 상태 머신, 출력 주소, 최신 합성 반영 여부를 나누어 확인했습니다.

가중치 내장 방식을 개발하는 동안 초기화 반복문, 개발 환경별 파일 경로와 합성 결과 반영 상태를 점검했습니다. 최종 통합에서는 AXI-Lite 런타임 가중치 로드 구조를 사용했습니다.

UART의 RAW 덤프와 상태 레지스터로 시작·진행·완료를 확인하고, 그 다음 영상 좌표 정렬을 살폈습니다. 현재·이전 프레임의 `tuser/tlast`, VDMA 읽기 시작 시점과 차분 덤프를 함께 비교하며 영상·가중치·제어 경계별로 원인을 좁혔습니다.

## 개발에 적용한 검증 방식

- 모델 평가는 동영상 단위 독립성을 확인하고, 평균 정확도와 실패 장면을 함께 살핍니다.
- 기능 시뮬레이션과 타이밍 검증을 구분합니다. 파이프라인을 넣을 때 데이터·상태·완료 신호의 지연을 함께 맞춥니다.
- 수정한 RTL, 생성한 bitstream, 내보낸 XSA, Vitis 플랫폼과 실행 파일의 버전을 맞춥니다.
- 결과가 없을 때는 UART·레지스터·프레임 덤프로 어느 경계까지 데이터가 도착했는지 확인합니다.
